# Ledger UX Improvement Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the HitSave Ledger (ledger.hitsave.org) safer and faster for archivists: actions report their outcome, risky actions confirm first, and every package gets its own page.

**Architecture:** The ledger is a stdlib `http.server` app (`ledger/app.py`) rendering HTML strings; `app.py` reads config at import, so all new logic goes in small importable modules under `ledger/` that tests load directly (pattern: `tests/test_catalog_correct_web.py`). No framework, no build step; JavaScript stays optional (progressive enhancement only).

**Tech Stack:** Python 3, psycopg 3, requests, plain HTML/CSS (`ledger/preserve_theme.css`), pytest run in the ingest-worker image (CI job `pytest`).

**Spec:** the UX review in this conversation (2026-11-06), summarised as phases below. Phases 1–2 are implemented on branch `ledger-ux-item-page`; phases 3–5 are follow-up PRs.

## Phases and effort

| Phase | What | Effort | PR |
|---|---|---|---|
| 1 | Action feedback + confirmations (visibility flash, quarantine confirm step, busy buttons, open-redirect fix) | ~0.5 day | this |
| 2 | Per-item page `/item?key=…`; table rows link to it; mutating actions move off the table rows | ~1 day | this |
| 3 | Clickable status/flag chips + `status` filter on `/` and `/health`; health attention "showing N of M" | ~0.5 day | next |
| 4 | Readable timestamps (`fmt_ts`) and status badges in all tables; truncated error cells | ~0.5 day | ledger-ux-badges |
| 5 | Correction form: prefill current Omeka values, keep/set/clear per field, before/after diff before applying | ~1.5 days | ledger-ux-correct-diff |
| later | `/ops` running/queued jobs, `/logs` tail view, page jump in pagination, `aria-sort` on `<th>`, light theme | small each | later |

## Global Constraints

- No new Python dependencies (image installs only `psycopg[binary] pyyaml requests boto3`).
- Pages must work with JavaScript disabled; JS only adds confirm dialogs and busy states.
- Omeka writes: visibility keeps its `o:is_public`-only PATCH (safe per the full-item rule: bodies with only `o:` keys leave values alone). Phase 2 adds **reads only** (GET item).
- Every user-supplied string rendered into HTML goes through `html.escape`.
- Redirect targets must be local paths: start with `/`, not `//`.
- Copy follows the archivist guide's plain-language style (no SQL/column names in sentences a non-admin reads; raw field names are fine in the "All fields" table).

## Review Focus

1. **Omeka unreachable or creds missing** when the item page loads → page still renders, visibility shows "Unknown", both Publish and Hide offered. (test in Task 3)
2. **`game_key` with spaces, slashes, `&`, unicode** → item links are URL-encoded and the lookup finds the row. (test in Task 3)
3. **Row without `omeka_item_id`** (not in Omeka yet) → item page renders, no visibility/correct/quarantine actions, says why. (test in Task 3)
4. **Visibility script fails** (bad id, Omeka 500) → user lands back where they were with a red notice carrying the script's last error line, not a silent redirect. (test in Task 1)
5. **`return_to=//evil.example`** or a missing/odd Referer → redirect falls back to `/`. (test in Task 1)

## Phase 5 tasks (branch `ledger-ux-correct-diff`)

**Decisions:** the ledger stays read-only toward Omeka (one GET of the item, the same one the item page does); the Windmill script `correct-catalog-item.py` keeps doing the write (full-item PATCH). The form is prefilled with the item's current values: title (`dcterms:title` as stored, else `o:title`), MobyGames URL (first non-`s3://` `bibo:uri` containing `mobygames.com`, else empty), description (all `dcterms:description` values, joined by a blank line), developers (`dcterms:creator`) and publishers (`dcterms:publisher`), joined with ", ". Per field: unchanged means keep; a new value means set; emptying developers or publishers means clear. Emptying title, description or the MobyGames URL is an error that says what to do instead; removing the MobyGames match stays an explicit checkbox because it also strips the release date, MobyGames rights and (unless set) credits, restores the press-kit description and resets the ledger match. Flow: edit → **Review** (only changed fields, now → after, plus side effects) → **Apply** or **Back to edit**. Review and Apply re-read Omeka and compare with the values the form was opened with (`orig_*` hidden fields); if the item changed meanwhile, nothing runs and the form comes back with the new current values and the person's edits kept. If Omeka can't be read, the form says so and offers no Apply (the Windmill job needs Omeka too).

## Review queue (branch `ledger-review-queue`)

**Why:** 1,747 complete press-kit packages are hidden in Omeka (2026-11-06: 1,093 Moby ok, 201 ambiguous, 453 no match) and need a check before publishing. A filter + item page means about four clicks per item; the queue is one.

**Decisions:** visibility lives in Omeka, so the ledger keeps the set of hidden item ids (`GET /api/items?is_public=0`, 1,000 per page, ~9 s for all) in memory for 10 minutes, and updates it right away when it publishes or hides an item itself. The queue holds `status = 'complete'` ledger rows whose Omeka item is hidden, oldest ledger id first, filterable by Moby status. One package per page: current values read fresh from Omeka (title, MobyGames link, description, developers, publishers), ledger Moby title/status, links to the item page and the Omeka admin. Actions: **Publish and next** (same script and audit as `/visibility`; no confirm dialog, since the button names exactly what it does and speed is the point), **Skip** (`?after=<id>`; wraps around at the end), **Correct…** and **Quarantine…** (both come back to the queue via `return_to`). No thumbnails (decided 2026-11-06). If Omeka can't be read, the page says so instead of showing a queue.
